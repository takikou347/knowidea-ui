# KNOW IDEA UI 0.9.0 と Ruleru の見た目の批評

結論は、書体とカバーを足した効果はあるが、内容に応じて強弱を決める編集がまだ弱い、ということ。
優先して直したいのは Ruleru の長い新着見出しと、公開済みの回より準備中の番組が大きく見える配分。
Murecho、主の色、角丸の段をもう一度取り替える必要は感じない。

これは [issue #9](https://github.com/takikou347/knowidea-ui/issues/9) への批評。
見た目から生成方法を判定するものではない。
以下の「AI っぽい」は、内容を入れ替えても成立する定型や、編集上の選択が見えにくい状態を指す。
決まりへの適合と、画面としての説得力も分けて考えた。

## 見た範囲と限界

- KNOW IDEA UI: main の `f5595847a702722cbacea6a0ac6351cdd83326ba`。`DESIGN.md`、`brand/README.md`、`packages/`、`apps/docs` を読んだ。
- UI をビルドし、トップ、Display、Jacket を Chromium で表示した。幅 390px・820px、ライト・ダークの全組合せを見た。
- Ruleru: main の `14398d9e1d6013ae2a4589e4f0fa7040573c7fa9` の `site/` をローカルで表示。同じ幅と配色で、新着、番組の棚、カバーを見た。
- `https://ruleru.pages.dev` はこの環境から HTTP 403。公開中の配信内容との一致、音声再生、実機での印象は未確認。Ruleru の指摘は上記コミットの公開用ファイルに対するもの。

画像は各幅・配色で確認したが、この変更は依頼どおり文書だけにした。
下の配置図は直し方の説明であり、実装済みの画面ではない。

## 残すもの

主の青緑は操作の入口を見つけやすい。本文との段差、直角の画像面、静かな背景も残したい。
ライトとダークでカバー自体を反転させない点は、作品の顔を保てている。

Ruleru のカバーは、汎用アイコンだけだった状態へ戻す理由がない。
キーボードの斜めの構図や、手と道具がある絵には、題材に触っている感じがある。
「聴く」「読む」と再生時間が近く、用途が選びやすい点も残す。

UI の操作できる見本、インストールの実コマンド、部品別の API・状態の表は実用的。
説明を飾るためにこれらを減らしたくない。
部品の見本を同じ枠で比べられることは、文書サイトでは長所でもある。

## 1. Ruleru の新着が、要約文を大きくした見出しになっている

**優先度: 高。型: 情報をすべて同じ強さで列挙する。**

トップの新着は「Claude Haiku 5.5 の公開から、Claude Code の長い会話の圧縮とフックの設定まで、この二週間の Claude の更新」。
モデル名、機能、期間が一度に太い見出しになり、何を一番聞かせたい回かが見えにくい。
390px でも820pxでも何行も続き、後者は画像の横の列に入るため、画面が広がっても見出しが短く収まらない。
根拠は `site/index.html` の新着と、`site/style.css` の `.row[data-lead] .row__title`。

これは大きな字そのものの問題ではない。
「大きな字を足せば個性が出る」という処方に、元の長い題をそのまま入れた結果に見える。

**直し方の案:** 一番の論点を短い主見出しにし、更新範囲はリードへ分ける。
例えば「Claude の更新、何が変わったか」を主見出しにして、モデル、圧縮、フック、期間を下で補う。
これは文言の候補で、番組の内容と制作部の判断で詰める。
元の正式な題や検索に必要な語を単に省略表示で隠す方法は避けたい。

**残す:** Murecho 800、最新の回を大きくする判断、番組名、日付、再生時間、聴く／読むの並び。

## 2. 準備中の番組にも、公開済みと同じ大きな売り場を与えている

**優先度: 高。型: 中身の量より、きれいな格子を優先する。**

確認したトップには公開済みの回が1件あり、4番組のうち3番組は「準備中」。
しかし番組の棚は、390px・820pxとも同じ正方形を2列で並べている。
公開済みの回を見たあと、まだ聴けない番組が大きく続く。
根拠は `site/index.html` の `.lineup` と、`site/style.css` の2列指定、1000px以上で4列になる指定。

棚をそろえること自体が悪いのではない。
現在の中身の偏りまでそろえて見せると、実際の活動より完成したサービスの外形が先に立つ。

**直し方の案:** 公開済みの番組はカバーと最新回、準備中は番組名と曜日の短い一覧にする。
4番組の予定を知れる入口は残し、作品が増えた時に棚を広げる。
架空の回や回数で空白を埋めない。

**残す:** 番組ごとの色とカバー、曜日、公開状況の明記。番組一覧のページでは同じ寸法で比較できてもよい。

## 3. カバーの違いが「題材の小物を差し替える」に留まりかけている

**優先度: 中。型: 同じ絵作りに別の小物と色を入れる。**

4枚とも、色の背景、ざらついた平面的な道具の絵、左下の白い太字、という組み合わせが近い。
ラジオ、タブレットとカップ、キーボード、本とカップで題材は区別できる。
一方、「Claude の情報をどう扱う番組か」「会社を何の視点で観察する番組か」までは絵から伝わりにくい。
根拠は `site/art/*-480.webp` の4番組のカバー。

同じ絵柄はシリーズとしての長所でもあり、全部違う画風にする必要はない。
ただ、道具の絵だけで題材を表すと、他社の同じ分野の番組にも移せてしまう。

**直し方の案:** 1番組ずつ、扱う具体物や問いを決めて絵に入れる。
キーボードなら配列や打鍵の違い、タブレットなら実際の使い方、会社なら判断や記録の関係など。
単に装飾を増やすのでなく、その番組を聴く理由につながる素材を選ぶ。

**残す:** 共通の質感、直角の面、明快な配色。特にキーボードの対角線の構図は違いとして活かせる。

## 4. Jacket を必須の顔にすると、別の定型を量産する危険がある

**優先度: 中。型: 禁止した型を、別の一種類の型で置き換える。**

Jacket の既定は、色の正方形、Murecho の題、下の補足。
縦組み、比率、揃え方を選べるため、部品の能力は狭くない。
しかし `DESIGN.md` の「顔」は、番組・回・記事・作品を Jacket に集める言い方になっている。
それを全作品へ機械的に当てると、アイコンのタイルを避けても、題字のタイルが均等に並ぶだけになる。
根拠は `packages/css/src/jacket.css`、`packages/ui/src/Jacket.tsx`、`apps/docs/src/demos/jacket.tsx`。

また、Ruleru の現在のカバーは文字を画像へ焼き込んだ `img`。
`DESIGN.md` の「題字は画像にせず文字で組む」と実際の出し方が食い違う。
`alt` には番組名があり、名前が全く取得できないという指摘ではない。
ただし字の拡大や組み直しが、画像内の文字には個別に効かない。

**直し方の案:** Jacket は文字で顔を作る時の選択肢として使い、並べる側で作品の優先度を決める。
Ruleru のカバーは絵を残し、番組名を外の文字でも出す案を比べたい。
画像内の題字を今後も使うなら、例外の扱いと文字情報の提供方法をデザイン部が決める。
決まりの変更案であり、この文書では変更しない。

**残す:** 角丸0、題字を本文から分ける考え、縦組みや比率の選択、隣と名前が重なる時の `decorative`。

## 5. UI のトップが、一般的なライブラリの紹介文から始まる

**優先度: 中。型: 大きな効能の見出し、2つのボタン、機能の説明。**

「React components for dense, themeable interfaces」は正確だが、他のUIライブラリにも置ける言葉。
820pxでは数行、390pxではさらに折り返し、最初に読ませる面積が大きい。
下には Theming、Accessibility、Dark mode、Icons が同じ調子で並ぶ。
根拠は `apps/docs/src/pages/index.astro` の `.hero` と `features`。

英語そのものや、アイコンが文字の隣にあることは問題ではない。
具体の強みを見る前に、よくある紹介ページの順番を長くたどる点が弱い。

**直し方の案:** 「詰めても操作できる」ことが分かる実物の画面を、短い説明と早く結び付ける。
既存の Live components の同じ画面で、密度、44pxの操作領域、配色変更を確認できるようにする。
機能の4項目は、一般的な美点の列挙より、その実物のどこを見ればよいかへつなげる。
根拠のない比較や利用者数は足さない。

**残す:** 左揃え、インストールのコマンド、2つの実際に使える入口、数値で説明した操作領域とコントラスト。

## 6. スマホでは「動く見本を全部置く」が選ぶ作業を重くしている

**優先度: 中。型: 網羅をそのままページの構成にする。**

トップの `picks` は18種類。390pxでは実際の画面見本に続いて、各部品が長い縦列になる。
その後に Features とカテゴリの入口が来る。
何があるかは分かるが、探す側は多数の枠を通り過ぎてから分類へ着く。
根拠は `apps/docs/src/pages/index.astro` の `picks`、`HomeLive`、節の順。

**直し方の案:** トップは代表的な操作に絞り、早い位置にカテゴリの入口を置く。
全見本とコードは Components と各部品のページで残す。
文書ページの同じデモ枠、props表、状態の表まで不規則にする必要はない。
比較するための反復と、紹介するための見せ場を分ける。

**残す:** 本物の操作、コピーできるコード、部品名、各ページの一貫した構成。

## 直す順と、配置の案

最初は Ruleru の1と2。続いてUIトップの5と6。
カバーの描き直しや、共有部品・決まりの変更は、画面の編集で足りない所を見てからにしたい。

幅390pxの案:

```text
新着
[カバー] 番組名
短い主見出し
更新の範囲を説明するリード
日付          [聴く 時間] [読む]

公開中の番組   [最新回へ]
準備中        番組名・曜日の短い一覧
```

幅820pxの案:

```text
新着
[カバー]  短い主見出し
          更新の範囲を説明するリード
          日付       [聴く 時間] [読む]

公開中の番組と最新回       準備中の番組・曜日
```

ライトとダークで情報の順番と面積は変えず、既存の各配色を使う。
カバーの色を反転させず、操作の主の色だけを既存のライト／ダークに従わせる。
これは批評のための配置案であり、色・書体・角丸の決まりを変更する提案ではない。

## 判断の確かめ方

変更前後を同じ実データ、390px・820px、ライト・ダークで並べる。
「何の回か」「今すぐ何を聴けるか」「どこから部品を探すか」を、画像を見た人に説明してもらう。
大きな字や絵を増やした数では評価しない。

定型に当てはまることだけでは不合格にしない。
題材を別のものへ替えても同じ見せ方になるか、反復に比較や操作の理由があるかを見たい。
本件では実装、デザインの正本、既存のカバー、公開サイトのファイルは変更していない。
